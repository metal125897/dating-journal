# Архитектура

Самостоятельный статический React/TypeScript-клиент на Vite для GitHub Pages. CSS по токенам исходного макета, без UI-конструктора. PostgreSQL/Neon через серверный драйвер; GigaChat через серверный REST-адаптер. Netlify Free Functions — опубликованный серверный API; интерфейс публикуется на GitHub Pages. Vercel исключён по прямому указанию владельца: аккаунт заблокирован. Облако прошло production smoke; доступ из двух сетей РФ ещё требует проверки владельцем.

```text
src/main.tsx             вход статического React-клиента
src/app/                 общий CSS
functions/               Netlify-обёртки HTTP и CORS
src/server/journal.ts    чтение и CRUD; полный экспорт клиентом из серверного снимка
src/server/ai.ts         серверные операции модели
src/components/          мобильный клиент и компоненты
src/lib/domain.ts        типы, валидация и чистые переходы
src/lib/repository.ts    PostgreSQL, версии и идемпотентность
src/lib/provider.ts      OAuth, TLS, квоты и структурированные ответы
src/lib/prompts.ts       версионируемые инструкции модели
migrations/              воспроизводимый SQL
scripts/                 миграции и проверки
tests/                   доменные и интеграционные проверки
public/                  только локальные ресурсы
references/              копии исходных материалов
docs/                    актуальная документация
```

## Хранение одной рабочей области

Для небольшого личного журнала выбран агрегат с PostgreSQL JSONB, типизированный серверной схемой. `journal_workspace` хранит настройки, людей, отчёты, разборы и ответы с общей ревизией. `journal_entries` хранит записи, физическую `event_date DATE` и метки времени `timestamptz`. Изменения выполняет SQL-функция: блокирует workspace, проверяет ревизию, сохраняет агрегат и записи атомарно. Эта простая схема сознательно ограничена одним владельцем и небольшим объёмом, не рассчитана на многопользовательскую CRM.

Чтение даёт цельный снимок. Клиент присылает конкретную команду, ожидаемую ревизию и UUID запроса. Сервер валидирует команду и применяет чистый доменный переход. Повторы возвращают тот же результат; конкурентная правка отклоняется с сообщением и обновлением снимка, введённый текст остаётся.

AI получает неизменяемый снимок одного человека. Блокировка операции в БД сериализует вызовы модели; квоты/частота проверяются на сервере. SQL-транзакция не остаётся открытой во время HTTP-запроса. После генерации сервер проверяет согласие, порог и основание и фиксирует результат короткой транзакцией. Разметка выполняется отдельным управляемым запросом, pending возобновляется при следующей загрузке; fire-and-forget нет.

Neon использует отдельный undici HTTPS Agent с двумя соединениями, без повторного использования idle-соединения (pipelining=0): стандартный fetch на локальном Windows-стенде воспроизводимо зависал при серии CRUD-запросов. Каждый SQL-запрос ограничен 10 секундами. GigaChat имеет независимый Agent с дополнительным официальным CA и обязательной проверкой TLS. Пустые пакеты вопросов не включаются в хеш основания; отправленные ответы и дописки включаются.

Демо — отдельное клиентское состояние с вымышленными данными. Ни один его запрос не обращается к БД или провайдеру. Browser storage хранит только черновики, не реальные сохранённые записи. Ключи `dj:draft:demo:*` и `dj:draft:live:*` разделены; старые ключи читаются только рабочим режимом. Отсутствие DATABASE_URL не включает демо автоматически.

Сетевой транспорт Neon допускает один повтор исключения fetch в пределах общего SQL timeout 10 секунд. UUID SQL-записи делает такой повтор идемпотентным. AI-lock использует отдельный случайный owner для каждой серверной попытки: повтор транспорта идемпотентен, повтор HTTP не запускает вторую модель параллельно. Пакет A со всеми пропусками не занимает lock модели.


Модуль evidence.ts строит реестр точных фрагментов; модель возвращает короткие ссылки, сервер разрешает их до канонических источников и проверяет результат. request-budget.ts изолирует общий deadline каждого AI-запроса через AsyncLocalStorage; транспорт модели и SQL используют оставшееся время.

AI запускается через короткий POST ai → внутренний ai-background. Клиент получает 202 и опрашивает ai-status по UUID. Фоновый worker атомарно захватывает отдельную техническую задачу, выполняет прежний проверенный серверный сценарий и сохраняет done/error; повтор UUID не запускает вторую модель. Результат читается из PostgreSQL, а не хранится в памяти функции. CORS проверяется до постановки. Ограничение контекста 55 000 символов также укладывается в payload фоновой функции. Background Functions доступны в Netlify Free. Потоковый эксперимент не устранит фактический 30-секундный обрыв и удалён.
